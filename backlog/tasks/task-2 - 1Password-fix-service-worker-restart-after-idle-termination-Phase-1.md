## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The single blocker for day-to-day 1Password use. On 2026-09-11 WebKit terminated the 1Password service worker about two minutes after its last activity (15:01:14); its three native messaging ports closed and Detour SIGTERMed the BrowserSupport processes. Every restart attempt afterwards (once per minute, a fresh WebContent process logging addRegistration) hung and timed out after ~30 s with WKWebExtensionError "The background content failed to load due to an error". The worker never ran again that session. Chrome also terminates idle workers and 1Password reconnects on wake, so the goal is a working restart, not preventing termination. Root cause unknown. Ordered experiments are in the plan: (1) api-explorer classic worker idle test to separate WebKit-general from 1Password-specific; (2) offscreen document WKWebView kept alive by OffscreenDocumentHost as a lingering client of the worker scope; (3) flip ExtensionManager.useModuleBundler to bundle the module worker into a classic script; (4) call WKWebExtensionContext.loadBackgroundContent on background-load failure; (5) keep-alive while a native port is open only as a last resort. Log filter for the run is in the plan; log show must run outside the Claude Code sandbox.

Data point from TASK-1 verification (2026-09-11, Debug build, isolated DETOUR_DATA_DIR=DetourVerify profile): TestExtensions/api-explorer classic worker fails at COLD START, not just after idle: WebKit fetches background.js and the imported _detour_polyfill.js successfully, creates the worker, then ~2 ms later logs ServiceWorkerContainer::jobFailedWithException 'Job 15 failed with error <private>' and terminates it; WKWebExtensionContextErrorDomain code=6 follows. A minimal probe extension (classic worker containing only console.* calls) loads and runs fine with the same injected polyfill, so the failure is in api-explorer's own background.js evaluation (some top-level API access throwing), not the polyfill. Experiment (1) in the plan should first get api-explorer loading at all; the exception text is <private> in the unified log, so read it via the console bridge or Web Inspector.

2026-09-11: Cold-start failure of api-explorer in the isolated profile was a harness artifact: no permission grant rows were seeded, WebKit hides ungranted API namespaces (chrome.alarms undefined), and the top-level access threw during worker evaluation. Found via a new bridge reporter for uncaught exceptions/unhandled rejections (ExtensionAPIPolyfill consoleJS, tested). Note for later: 1Password calls browser.alarms.* extensively, so alarms is load-bearing for it too.

2026-09-11 experiment results (Debug build, isolated profiles, 1-minute periodic alarm as the wake source): (a) classic-worker probe and api-explorer: WebKit unloads the background 30 s after each load, the worker is terminated, and every alarm wake succeeds with a FRESH registration (addRegistration -> script fetch -> 'Created service worker') for 8 minutes straight. (b) module-worker probe: identical, restarts every minute -> module type is NOT the cause; experiment 3 (bundler) is ruled out. (c) production (old build, 1Password, observed live 17:13-17:16): each wake logs addRegistration -> 'jobResolvedWithRegistration: Registration job succeeded' instantly with NO script fetch and no new worker (the 'directly reusable registration' path in SWServerJobQueue::runRegisterJob), then exactly 30 s later WKWebExtensionContextErrorDomain code 6. WebKit source (UIProcess/Extensions/Cocoa/WebExtensionContextCocoa.mm + WebPageProxy.cpp): the background 'load' is a hidden page calling navigator.serviceWorker.register(); success is reported via willSettleRegistrationPromise -> didFinishServiceWorkerPageRegistration; scheduleBackgroundContentToUnload fires 30 s after load/wake (2 min while ports are active) and unloadBackgroundWebView -> WKWebView _close -> callLoadCompletionHandlersIfNecessary(false) turns a still-pending load into code 6. So in production the completion is still pending 30 s after the wake: the reused registration never installs/starts a worker. Upstream WebKit commit 4ce58a7ff7 (2026-08-31, bug 322881, 'Extension service worker loses clients when it is unloaded and reloaded', test WKWebExtensionAPIOffscreen) changed exactly this area: registrations with other live clients (offscreen document) now survive the SW page disconnect and reconnect on re-register. Prime suspect: Detour's OffscreenDocumentHost WKWebView (created with the context's configuration, never closed) is a lingering client of the worker scope. Offscreen-client probe run in progress.

Offscreen-client probe (classic worker + never-closed offscreen document, DetourVerify3): restarts fine every minute; the Debug app's network process logs 'SWServerRegistration::clear' at each unload and every wake creates a fresh registration. So a lingering offscreen document alone does NOT reproduce; experiment 2 is ruled out in isolation. Network-process log of the PRODUCTION app (PID 86662) confirms the failure signature directly: every wake logs 'SWServerJobQueue::runRegisterJob: Found directly reusable registration 36/33 (DONE)' - the two registrations created at the 14:56 launch were never cleared when the background unloaded at 15:01, so re-registration reuses them, no worker is created, and the pending load fails 30 s later. The 14:56-15:05 history is no longer in the log store. Next: run the real 1Password extension in an isolated Debug profile (DetourVerify4) with a live log stream of both Detour and the network process to catch the first unload; native messaging will be untrusted there (BrowserSupport logs double as the TASK-6 data point).

1Password itself in the isolated Debug profile (DetourVerify4, all permissions granted, BrowserSupport rejects the build so native ports close immediately): the module worker restarts cleanly every minute for 6+ minutes; network process logs 'No existing registration ... constructing a new one' + 'SWServerRegistration::clear' on every cycle, with the offscreen document created and the console bridge showing 1Password's real exception text. So module type, offscreen document and 1Password's own startup code are all fine; the only production ingredient the harness lacked was a native port that stays OPEN (trusted host), which switches WebKit's unload to the 2-minute delayForInactivePorts path. Added a Debug-only DETOUR_NATIVE_MESSAGING_HOSTS_DIR override in NativeMessagingHost.searchDirectories and a silent fake host (keeps stdin open, never replies) to reproduce that path without trust; run in progress.

Native-port probe (classic worker holding a native port to a silent fake host, active for 60 s then quiet, DetourVerify5): WebKit took the 2-minute inactive-ports path (unload at +2.5 min after last message), ports closed, registration cleared, next alarm created a fresh worker. So the open-port path is clean in isolation too. Live capture of one production cycle (17:53:44): the new hidden SW page for the Default context is placed into the ORIGINAL WebContent process 86667 (alive since 14:56); register() resolves as reusable with 'ServiceWorkerRegistration: ID 36 active=50' and 'ServiceWorker::serviceWorkerID=50, state=4' (activated), and the network process registers the page as a client of remote worker process 86668 - i.e. the SW server still believes worker 50 is alive in the old process. In the last 75 min the production network process logged nothing but 'Found directly reusable registration' (150x): no terminate, no clear, no context-connection change. Conclusion: production is stuck because the server-side registration/worker was never torn down when the background unloaded at 15:01; the harness always tears it down (SWServerRegistration::clear at unload). Trigger for the missing teardown still unknown.

Fix implemented (2026-09-11 evening), two layers. (1) Prevention, Chrome parity: ExtensionAPIPolyfill.nativePortKeepAliveJS wraps runtime.connectNative in the worker; while >=1 real native port is open it holds a port to Detour's own 'detourPolyfill' host and posts {type:'keepalive'} every 45 s. WebKit counts any message posted by the background page on any port as activity (WebExtensionContext::portPostMessage), so the 2-minute inactive-ports unload never fires while a native port is connected; the keep-alive stops when the last real port closes so normal unload resumes. ExtensionManager's connectUsing delegate accepts 'detourPolyfill' ports without spawning a host (keepAlivePorts). (2) Recovery: Profile's errorsDidUpdate observer detects WKWebExtensionContext.Error.backgroundContentFailedToLoad and calls recoverFromBackgroundLoadFailure, which unloads and reloads the context in that profile (new base URL -> new origin -> the stale registration is irrelevant), re-associates windows/tabs, and calls loadBackgroundContent; rate-limited to 3 reloads per 10 min per extension. unloadExtension now also stops the extension's OffscreenDocumentHost. Verification runs in progress: keep-alive with the native-port probe (port held 3 min then disconnected), recovery with a throwing worker.

Keep-alive install detail: in a real WebKit worker, chrome.runtime.connectNative is a non-writable own property (writable:false, configurable:true) that silently ignores both assignment and Object.defineProperty, so the wrapper cannot be installed in place (first keep-alive run showed livePorts 0 and the worker still unloaded at +2.5 min). chrome and browser are the same object and plain writable globals, and a Proxy over runtime that binds real functions to the real runtime keeps getURL/id/getManifest/events/lastError/connectNative working (a prototype-chained shadow breaks getManifest). The polyfill now tries direct replacement first and, in service worker contexts only, falls back to shadowing the chrome/browser globals with such proxies. Rebuilt; keep-alive verified engaging (native port connected; keepalive active: true livePorts: 1).

Keep-alive verified in the harness (native-port probe, 2026-09-11 18:14): with the port held open and no traffic, the worker survived the full 3 minutes (previously unloaded at +2.5 min); when the probe released the port the keep-alive stopped, WebKit unloaded the background 30 s later, and the next alarm created a fresh worker which reconnected and re-armed the keep-alive. Recovery verified with a throwing worker: 3 context reloads then give-up. ExtensionPolyfillTests: 67/67 (8 new keep-alive tests; the test shim now runs before the polyfill, which the harness previously got backwards). Remaining for this task: production verification with the signed /Applications build and real 1Password (AC1/AC2), and api-explorer idle restart with a wake source (AC3).

ROOT CAUSE FOUND (2026-09-11 18:45, production, new build deployed to /Applications at 18:31): sampling the hidden background page's WebContent process (38757) showed its MAIN THREAD deadlocked: WorkerMainRunLoop -> microtask -> 1Password JS -> new WebSocket() -> WebSocket::connect -> WorkerThreadableWebSocketChannel ctor -> BinarySemaphore::waitUntil (waiting for the main thread to create the channel). WebKit runs an extension service worker on the main thread of its process, so a worker WebSocket is a self-deadlock. Consequences match every observation: the worker's event loop freezes (no keep-alive pings, ports go quiet), WebKit's unload closes the page but the frozen process never handles the close, so the SW client is never unregistered, the registration is never cleared, the worker/process linger silently for hours, and every wake reuses the registration with no worker (loudly with code 6 when the new page lands in a reused process, silently otherwise). 1Password's WebSocket is its server push notifier (@1password/web-api Notifier, optional: 'Notifier not available'). The harness never reproduced because without a desktop session 1Password never reaches that code. Upstream WebKit main still has the synchronous wait. Fix: worker-only WebSocket guard in the polyfill that fails the connection asynchronously (error + close 1006), real constructor kept as __detourNativeWebSocket; the keep-alive and recovery layers stay as defense in depth. Production side effect until redeploy: 1Password on the 18:31 build is dead again since 18:33:40.

WebSocket guard verified in the harness (WebSocket probe, DetourVerify8): the worker constructs the socket, receives error then close(1006), is still alive 5 s later, unloads at +30 s and restarts on every alarm with fresh registrations. ExtensionPolyfillTests 75/75 (8 guard tests). Fixed build redeployed to /Applications at 18:50:17 (PID 44025): three hosts connected, keep-alives armed; at +4 min no port disconnects, no worker termination, no hidden-page close, and the hidden-page process main thread is idle in its run loop (the 18:31 build was dead at +2.5 min). 15-minute check pending.

Harness run 18:55-18:59 (DetourVerify, permissions granted): its worker is unloaded 30 s after each start and restarted by every heartbeat (4 starts per profile in 4 minutes, fresh registration each time).

PRODUCTION VERIFIED (build deployed 18:50:17, PID 44025): at 19:05, 15 idle minutes after launch with no interaction, the three BrowserSupport helpers spawned at 18:50:19 are still alive (native ports open), the three hidden-page content processes are alive with main threads idle in their run loops, no worker termination/creation beyond the initial three, no code 6, no recovery reload. The 18:31 build (same code minus the WebSocket guard) had all ports closed and the worker frozen at +2.5 min. AC1 (restart after idle termination + port reconnect) demonstrated with real 1Password in the harness: after each 30-s unload the next alarm created a fresh worker and 'Connected to native host' followed; in production the keep-alive means termination only happens once 1Password itself drops its ports. ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Root cause: WebKit runs an extension service worker on the main thread of its content process, and 1Password's worker calls new WebSocket() (server push notifier); WorkerThreadableWebSocketChannel blocks the calling thread waiting for the main thread, so the worker deadlocks itself. The frozen process never handles WebKit's idle unload, so the worker's registration is never cleared and every wake reuses a registration with no worker (1Password dead until relaunch). Fix, three layers in the polyfill/Profile/ExtensionManager: (0) worker-only WebSocket guard that fails connections asynchronously (error + close 1006) instead of deadlocking; (1) Chrome-parity keep-alive: while a real native port is open the worker pings a Detour-owned port every 45 s so WebKit's 2-minute inactive-ports unload never fires (installed by shadowing chrome/browser with proxies because WebKit's runtime.connectNative is not replaceable); (2) recovery: on backgroundContentFailedToLoad the context is reloaded in that profile (new origin), rate-limited 3/10 min. Also: uncaught worker exceptions reported through the console bridge, Debug-only DETOUR_NATIVE_MESSAGING_HOSTS_DIR override, api-explorer heartbeat alarm. Verified: 75/75 ExtensionPolyfillTests; harness probes for guard, keep-alive, recovery, and restarts; production 15-minute idle run with ports and workers alive. Documented in docs/1password-integration-plan.md Phase 1. Follow-ups proposed: WebSocket relay over the polyfill port; WebKit bug report.
