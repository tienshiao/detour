## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
After many hours of uptime (17h on Sep 21 2026) Detour's com.apple.WebKit.GPU process holds ~16.7k IOSurface mappings against the per-client limit of 16384. From then on every IOSurface allocation fails ('IOSurface creation failed: e00002be … likely per client IOSurface limit of 16384 reached', category com.apple.WebKit:Layers, thousands per hour), WebGL contexts are lost in every page, and YouTube — whose BotGuard attestation fingerprints WebGL/canvas — flags the session and serves a deliberately garbled player response: videoplayback URLs with sig == lsig, expire == mt (year 2079), a random foreign ip= (14.94.78.84, Korea Telecom, while the Mac's egress was 99.6.251.168) and KT-region CDN hosts that NXDOMAIN from here. Symptoms the user sees: 'An error occurred. Please try again later.', console 'A server with the specified hostname could not be found (videoplayback)', 403 on videoplayback, 'WebGL: context lost', and 1Password's content-script fetch of its own webkit-extension:// resource failing. Content blocking on/off makes no difference; reload does not help; restarting Detour fixes it because the GPU process restarts. Session had 16 tabs in 2 spaces yet 23 WebContent processes.\n\nvmmap of the GPU process: 16,682 IOSurface regions, of which 15,900 are PURGE=E (volatile and already purged, 0 resident) and only 781 PURGE=N; the UI process maps 2,366. So these are backing buffers WebKit marked volatile for non-displayed pages, the kernel emptied them, and the IOSurface objects were never destroyed — the count grows with time, not memory. Size histogram: 7181x16K, 1371x48K, 920x32K, 857x64K, 583x1040K (512x512 tiles), 529x2800K. Not DNS, not a proxy/VPN (Tailscale had no exit node; all Networking-process flows were on en8; the machine never slept or changed network since launch).\n\nOpen question is the leak source: retained RemoteLayerBackingStore/ImageBuffer sets for pages Detour keeps alive (one WKWebView per tab, plus pinned/favourite/peek/extension views), buffers orphaned on tab show/hide (container.removeFromSuperview in BrowserWindowController), or a WebKit bug on this macOS (Darwin 25.6). Measure with: vmmap --summary <gpu pid> | grep IOSurface (region count, last column) and vmmap <gpu pid> | grep '^IOSurface' | grep -c PURGE=E, both need the sandbox off; log show --predicate 'processIdentifier == <gpu pid> AND eventMessage CONTAINS "per client IOSurface limit"'. Compare growth per action in the harness: idle heavy page, SPA navigations on a hidden tab, repeated tab switches, ownership transfer between windows, peeks, opening/closing tabs; check whether closing a tab returns its surfaces.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. BrowserTab: add showsSinceWake (Int, reset whenever a web view is created: init with a web view, wake()) and noteShown(). BrowserWindowController increments it for every pane it hosts (claimSingleWebView / claimSplitWebViews, which also covers window-focus ownership transfers) and for the hosted panes + open peek when the window's occlusion state flips to visible (NSWindow.didChangeOcclusionStateNotification), so app switching counts too.
2. TabStore.sleepStaleTabs: keep today's rule (normal, unpinned tabs idle >= profile.sleepThreshold) and add a second trigger for ANY hidden, silent tab — space tabs, pinned entries' backing tabs, favourites' backing tabs (profile.favorites[].tab) — idle (lastDeselectedAt) >= sleepShowBudgetGrace (15 min) once showsSinceWake >= sleepShowBudget (50). Split partners keep the both-stale rule. Sleeping a favourite/pinned backing tab must keep the entry live (tab retained, just asleep) and wake through the existing claimWebView -> wakeIfNeeded path; verify ExtensionTabLifecycle stays consistent (a sleeping tab is still 'open').
3. Constants live in one place (TabStore) with a DEBUG env override (DETOUR_SLEEP_SHOW_BUDGET / DETOUR_SLEEP_SHOW_BUDGET_GRACE_SECONDS) so the harness can exercise the rule in minutes.
4. Tests: sleep policy unit tests (budget reached + grace elapsed sleeps pinned/favourite/normal tabs; budget reached but grace not elapsed does not; budget not reached follows the old rule; audio and fresh split partners still block; counter resets on wake; occlusion increments). Existing BrowserTabWakeTests / ExtensionTabLifecycleTests cover the wake side.
5. Verify in the harness (docs/task-104/task104-harness.patch + run_harness.sh, budget=20, grace=30s): after the switching phases and a settle > grace, hidden tabs sleep and the GPU IOSurface count drops back near the single-visible-tab baseline; no 'IOSurface creation failed' in the GPU log.
6. Follow-ups filed separately: GPU-process recycle valve gated on app-inactive + nothing playing (covers the visible tab's occlusion churn), and a WebKit bug report for IOSurfacePool's byte-only cap.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Run 1 (fixture: 4 tabs x 400 will-change:transform layers repainted every 200ms): GPU process holds only ~30-70 IOSurfaces; the fixture's small layers do not land in the GPU process at all (only 512x512 tiles do), so this fixture cannot reproduce the prod histogram (7181 x 16K). Tab switching phase flat at 68. Run 2 uses real pages (YouTube watch + home, GitHub, apple.com).

Run 2 (real pages: YouTube watch, YouTube home, github.com/WebKit/WebKit, apple.com; 4 tabs, 2x150 selectTab switches @0.7s, 45s settles): GPU IOSurface total 670 (idle) -> 1647 after switch1 -> 1708 after settle1 -> 1997 after switch2 -> 1997 after settle2 -> 1495 after closing 3 tabs -> 1496 with ONE tab left (755 PURGE=E). Idle/settle phases are flat; only show/hide cycles grow the count (~2-4 surfaces per switch, purged count rising in lockstep); closing tabs frees only their live buffers, ~1200 surfaces stay orphaned in the GPU process. Reproduces the prod signature (16 tabs / 16.7k surfaces) in 8 minutes; video playback is not required (harness tabs were not playing). Next: standalone plain-WKWebView control with the same pages and removeFromSuperview/addSubview cycling to tell WebKit bug from Detour hosting.

Mechanism (WebKit source, main as of Sep 2026): the GPU process keeps one WebCore::IOSurfacePool per WebContent connection (GPUConnectionToWebProcess::sharedResourceCache()->ioSurfacePool(), RemoteRenderingBackend passes it as creationContext.surfacePool). Released layer buffers go into that pool; IOSurfacePool::collectionTimerFired only marks idle surfaces volatile (surfaceAgeBeforeMarkingPurgeable 2s) -> the kernel purges them (vmmap PURGE=E, 0 resident). The pool evicts by BYTES only (defaultMaximumBytesCached = 256 MB on PLATFORM(MAC), 64 MB elsewhere; FIXME in evict() acknowledges purged surfaces pile up) and discards everything only on memory pressure, which purged surfaces never cause. Nothing caps the surface COUNT, while the kernel caps the GPU process at 16384 IOSurfaces. Prod: 23 WebContent connections x ~256 MB = 5.6 GB virtual = 16.7k surfaces, mostly 16-64K buffers from small layers repainted on every tab show. Standalone plain-WKWebView control (scratchpad spike, removeFromSuperview/addSubview cycling, same 4 pages) grows the same way: 533 idle -> 1021 after 150 switches -> 1084 mid switch2, so this is WebKit behaviour, not Detour hosting. Detour is exposed by keeping many WebContent processes alive for days (16 tabs -> 23 processes: pinned/favourite/peek/extension views + process-swap/bfcache processes) and by tab switching repainting each page's layers into fresh pooled buffers.

Control result (plain WKWebView spike, docs/task-104/main.swift): 533 idle -> 1021 after switch1 -> 1343 after switch2 -> 1458 end; identical shape to Detour run 2, so AC1 is met: the growth is WebKit's per-connection IOSurfacePool retaining purged buffers, triggered by every hide->show repaint; Detour's hosting is not at fault. Harness patch, sampler scripts, spike source and CSVs saved under docs/task-104/ (AppDelegate harness reverted from the tree). Not yet decided: mitigation — (A) unload hidden tabs' web views after N idle minutes (frees that connection's pool; Detour run 2 showed closing tabs returns their pool), (B) proactively recycle the GPU process when idle after long uptime (WebKit relaunches it and pages reconnect via gpuProcessConnectionDidBecomeAvailable, but WebGL contexts are lost and playing media is interrupted; too many exits in a window make WebKit kill all web processes), (C) both, plus a WebKit bug report asking IOSurfacePool to cap by count / drop purged surfaces.

Occlusion control (spike mode occlude, one YouTube view, window orderOut/orderFront 2x90): 433 -> 695 after the first 90 cycles (+2.9/cycle) -> 769 after the second 90 (+0.8/cycle). Window occlusion / app switching churns the VISIBLE tab too, so Detour cannot count every hide->show; growth is front-loaded per page (size-matched pool reuse kicks in once layer sizes stabilise) and is sustained mostly by pages whose layer sizes keep changing (SPAs navigating: YouTube, Gmail, Calendar). Decision with the user (Sep 21 2026): go with more aggressive unloading, but a show budget must not sleep a tab right after use — it shortens the idle threshold instead.

Implementation (Opus agent, worktree agent-a9da6b57edcd9cb80): BrowserTab.showsSinceWake/noteShown (reset in wake), BrowserWindowController counts at claimSingleWebView/claimSplitWebViews and on window occlusion not-visible->visible, TabStore.sleepShowBudget (50, env DETOUR_SLEEP_SHOW_BUDGET) / sleepShowBudgetGrace (15 min, env DETOUR_SLEEP_SHOW_BUDGET_GRACE_SECONDS), sleepStaleTabs(now:) adds the budget rule for normal tabs, pinned entries' and favourites' backing tabs (sleep(), entries stay live), honours sleepThreshold == .never, refuses tabs whose container is parented in some window. 14 new tests in SleepShowBudgetTests + wake/lifecycle/move/pinned/split/store suites green (201 tests). Run 3 (harness on the worktree build, budget 20 / grace 30s, 4 real pages, 2x100 switches): showsSinceWake=[52,50,50,50]; sleepStaleTabs slept the three hidden tabs (selected tab untouched); GPU IOSurface count 1649 -> 1317 within 5 s (UI 848 -> 628), zero 'IOSurface creation failed'. Remaining ~1300 is the visible YouTube watch tab's own pool: that page churns ~25 surfaces per show vs ~3 for GitHub/apple.com/YouTube home — the visible-tab occlusion case is TASK-105's. Data: docs/task-104/run3-sleep-policy.csv.

Validation: full DetourTests run on the merged tree — 1545 tests, 4 failures, all pre-existing flakes unrelated to this change (FavoriteFaviconTests x2 = TASK-98; ExtensionPolyfillIntegrationTests.testStorageManagedInRealExtensionContextSurvivesGarbageCollection GC timing); each passes when re-run in isolation. AC4: the retention is inside WebKit; mitigation = show-budget sleep rule (this task), backstop = TASK-105 GPU recycle valve, upstream = TASK-106 bug report; WebKit references: IOSurfacePool.cpp evict()/collectionTimerFired, IOSurfacePool.h defaultMaximumBytesCached, GPUConnectionToWebProcess::sharedResourceCache.

Review pass on the show-budget change (uncommitted): (1) claimSingleWebView/claimSplitWebViews now count a show only when the pane is actually (re)attached — the refresh branch runs on every windowDidBecomeKey (popover close, Cmd-Tab) and nothing ever hides the container, so counting it double-spent the budget; (2) space switch and window close stamp the outgoing tab's lastDeselectedAt via stampDeselected (selectTab cannot, activeSpaceID has already moved) — before this a pinned tab left behind by a space switch never slept under either rule; (3) the 'hosted somewhere' (container has superview) guard is shared by both rules (offScreenSince) so the idle rule no longer blanks a second window on a shared space; (4) grace override rejects non-finite values; (5) dropped the dead peek count. Tests: SleepShowBudgetTests 15/15.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Diagnosed 'YouTube stops playing after hours' (403 videoplayback, NXDOMAIN CDN hosts, WebGL context lost) as WebKit's GPU process exhausting the kernel's 16,384-IOSurface limit: one byte-capped IOSurfacePool per WebContent process retains purged buffers on every hidden->visible transition, YouTube's BotGuard then fails and serves a poisoned player response. Reproduced in 8 minutes with a Detour harness and a standalone plain-WKWebView spike (docs/task-104). Mitigation: a 'show budget' — BrowserTab.showsSinceWake counted at every hosting and window de-occlusion; once a hidden, silent tab has been shown 50 times (DETOUR_SLEEP_SHOW_BUDGET) it sleeps after 15 min out of sight (DETOUR_SLEEP_SHOW_BUDGET_GRACE_SECONDS) instead of the profile's 1 h threshold, pinned entries' and favourites' backing tabs included (they stay live-but-asleep and wake with their interaction state); never sleeps a visible or freshly used tab. Verified: 14 new unit tests + related suites; harness run with budget 20 / grace 30 s slept the hidden tabs and dropped the GPU IOSurface count 1649 -> 1317 within 5 s with zero allocation failures. Follow-ups: TASK-105 (GPU-process recycle valve for the visible tab's occlusion churn), TASK-106 (WebKit bug).
